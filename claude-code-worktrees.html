Claude Code and git worktrees

A worktree gives each agent its own checkout on its own branch. It takes one command. The part nobody warns you about is that the new folder has no node_modules and no .env, so the first thing your agent does is fail.

Written 16 October 2026, updated 17 October.

One command

$ git worktree add ../app-dark-mode -b dark-mode
Preparing worktree (new branch 'dark-mode')
HEAD is now at 4a1c9f2 Snooze survives a restart

You now have a second folder, checked out to a new branch, sharing one object store with the first. No second clone, no copy of the history.

Point an agent at that folder and it cannot touch anything in your main checkout. That is the whole reason worktrees and parallel agents go together.

What goes wrong without one

Two Claude Code sessions in one folder share one working tree. Both edit the same files. Both run the formatter. Both commit.

The result is not a merge conflict. Git never sees two versions, so it has nothing to resolve. You get one diff with two half-finished ideas interleaved, and neither agent knows the other exists.

The first failure: an empty folder

A worktree holds what is committed. Everything git ignores stays behind. For a typical Node project that means the new folder has no node_modules, no .env, and none of the local config your build reads.

So the agent starts, runs the tests, and gets this:

$ npm test
sh: vitest: command not found

You can fix it by hand every time with npm install in each worktree, which is slow and duplicates a few hundred megabytes per task. Or you can declare the ignored files worth carrying.

.worktreeinclude

A file at the repository root, in gitignore syntax, naming the ignored files a new worktree should receive. Claude Code reads it. Conductor reads it. Agentbox reads it. It is the closest thing this category has to a shared convention, and most people have never heard of it. Nick Khami's write-up on worktrees, agents and tmux is the best account of the workflow this solves.

node_modules/
.env
.env.local
!.env.production

Git does the matching, with git ls-files --others --ignored --exclude-from, so negation, anchoring and globs behave exactly as git defines them. On macOS the copy asks APFS for a block-sharing clone, so carrying node_modules across costs almost no disk.

One warning, because it is a real way to leak a secret. That git command does not consult your .gitignore. A pattern that selects a file the repository does not actually ignore leaves it untracked in the new folder, and anything that later runs git add -A will commit it. Agentbox checks every selected path with git check-ignore in both checkouts before carrying it, and refuses the whole folder by name if one fails. If you are rolling your own, do that check too.

Cleaning up

This is where worktrees actually bite. Abandoned runs leave folders and branches behind, and after a fortnight you have thirty of each.

$ git worktree list
/Users/you/app              4a1c9f2 [main]
/Users/you/app-dark-mode    8b31e07 [dark-mode]
/Users/you/app-snooze       1f90a42 [snooze-restart]

$ git worktree remove ../app-dark-mode
$ git worktree prune          # drop records whose folders are already gone
$ git branch -d dark-mode     # the branch is separate

Two traps. git worktree remove refuses while the folder has uncommitted changes, which is right nearly every time and infuriating the once it is not. --force overrides it.

And removing a worktree never deletes its branch. A clean git worktree list sits happily beside a git branch output thirty lines long.

Where tools put them

There is no standard, which matters the moment you use two tools on one repository. Claude Code, Codex, Orca and Superset each choose their own directory, and a user comparing them on Hacker News on 15 October 2026 named exactly that as the annoyance.

Agentbox uses .claude/worktrees/<task id> inside the repository, with a branch of the same name, so a task called w-7c21 works in .claude/worktrees/w-7c21 on branch agentbox/w-7c21. Inside the repository needs a .gitignore entry, which is the cost of that choice.

Whatever you pick, git worktree list --porcelain is the ground truth, and it is what tools read to find out what they left behind.

Worktree or branch?

A branch is enough when you work on one thing at a time. Switching branches in one folder is simpler, needs no cleanup, and keeps a single node_modules.

A worktree earns its keep when two things must exist at once. Two agents working at the same time. A dev server you do not want to restart. A review of someone else's branch without stashing your own work.

For one person, branches are usually fine. For several agents, worktrees are close to mandatory.

Merging one back

$ git merge dark-mode
$ git worktree remove ../app-dark-mode
$ git branch -d dark-mode

Nothing special. The branch is an ordinary branch.

The part that gets harder with many agents is not the merge. It is the deciding. More on running several at once. Five finished branches need five reviews, and reading five diffs in a terminal is where the time goes.

Two questions people ask

Is it safe to run several agents in worktrees at once?

For files, yes. They cannot reach each other's checkouts. The shared parts are the object store, which git is built for, and anything outside git. If your dev server binds a fixed port, two agents starting it will collide, and that has nothing to do with worktrees.

Can I turn worktrees off in a tool that creates them?

Usually, and check before you adopt one. A tool that insists on a worktree per task will fight a repository with submodules, or generated files that are ignored but required, or a build that writes outside the tree.
