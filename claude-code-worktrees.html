Claude Code and git worktrees

A worktree gives an agent its own checkout of your repository on its own branch, in its own folder. It is the one piece of plumbing that makes running several agents at once safe, and it is the thing people then have questions about.

Written 16 October 2026.

What a worktree actually is

One git repository can have several working directories at once. git worktree add makes another folder, checked out to its own branch, sharing the same object store and history. Two checkouts, one repository, no copying of history and no second clone.

git worktree add ../myrepo-feature-x -b feature-x

For agents this is exactly the right shape. Each agent edits files nobody else is editing, commits to a branch nobody else is on, and you merge the ones that worked.

Why it matters for parallel agents

Without it, two Claude Code sessions in one folder share one working tree. Both edit the same files, both run the formatter, both commit. What you get is not a merge conflict you can resolve — it is two half-finished ideas interleaved in one diff, with neither agent aware the other exists.

With a worktree each, the failure mode goes away completely. The agents cannot see each other's files. The work converges at merge time, where git is actually good at this.

Where they live

There is no universal answer, and it is a real annoyance: different tools put them in different places. Common choices are a sibling folder next to the repository, a folder inside the repository, or a central directory somewhere under your home.

Inside the repository is tidy but needs a .gitignore entry, or git will offer to commit the worktree folder into the repository it came from. Agentbox puts each one under .claude/worktrees/ in the repository and names it after the task.

Whatever you choose, git worktree list is the ground truth:

git worktree list

Cleaning up

This is where worktrees actually bite. Abandoned agent runs leave folders and branches behind, and after a few weeks you have thirty of each.

git worktree remove ../myrepo-feature-x
git worktree prune          # drop records whose folders are already gone
git branch -d feature-x     # the branch is separate; removing the worktree does not delete it

Two traps worth knowing. git worktree remove refuses while the folder has uncommitted changes, which is usually correct and occasionally infuriating — --force exists and does what it says. And removing a worktree never deletes its branch, so a tidy git worktree list can still sit alongside a very untidy git branch.

The other thing nobody warns you about: node_modules. A new worktree is a fresh checkout with no installed dependencies, so most projects need an install per worktree. It is why "just make a worktree per task" is cheaper in git than it is on disk.

Worktree or just a branch?

A branch is enough when you work on one thing at a time. Switching branches in one folder is simpler, needs no cleanup, and keeps a single node_modules.

A worktree earns its keep when two things must exist at the same time: two agents working at once, a long-running build or dev server you do not want to restart, or a review of someone else's branch without stashing your own work.

For a single human, branches are usually fine. For several agents, worktrees are close to mandatory.

Merging one back

Nothing special — the branch is an ordinary branch:

git -C . merge feature-x       # from your main checkout
git worktree remove ../myrepo-feature-x
git branch -d feature-x

The thing that is genuinely harder with many agents is not the merge, it is deciding. Five finished branches need five reviews, and reading five diffs in a terminal is where the time actually goes. Whatever you use, make sure you can see the diff.

Common questions

Is it safe to run several agents in worktrees at the same time?

For the files, yes — that is the entire point, and they cannot reach each other's checkouts. The shared parts are the object store, which git is built to handle, and anything outside git: a database, a port, a cache directory. If your dev server binds a fixed port, two agents starting it will collide, and that has nothing to do with worktrees.

Do I have to use them?

No. You can run agents sequentially in one checkout and never think about this. Worktrees are the price of parallelism, not of using an agent.

Can I turn them off in a tool that creates them?

Usually yes, and it is worth checking before you adopt something, because a tool that insists on a worktree per task will fight a repository that is not set up for it — git submodules, generated files that are gitignored but required, or a build that writes outside the tree.

How Agentbox handles it

Every task gets its own worktree under .claude/worktrees/ and its own branch, created when the task starts. The built-in terminal opens in that folder, so the commands you type land where the agent is working, and the diff is shown in the app when the agent is done. You review and merge from there.

That is a convenience, not a monopoly: it is ordinary git underneath, and git worktree list in your repository will show you exactly the same thing.
